# Desktop (Tauri v2)

Check `desktop/Cargo.toml`, `desktop/capabilities/**`, and `desktop/tauri.conf.json` before adding desktop capabilities. Release versions are also set in `desktop/tauri.conf.json` and `desktop/Cargo.toml` (`tools/AGENTS.md`, Releases).

- File system and shell permissions must be configured explicitly; a vague "Internal error" save failure usually means a missing permission.
- Dev tools: add or use a menu item to toggle them; do not rely on keyboard shortcuts.
- `desktop/src/credentials.rs` stores secrets in the native system credential store; failures must surface, never fall back to browser or plaintext storage (`src/AGENTS.md`, Settings).
- ACP and harness process changes require checking `desktop/capabilities/**`.
- The fs scope allows documents anywhere but denies, in the global `fs:scope`, every place where a written file would run, and `requireLiteralLeadingDot` keeps hidden files out of `**` on every platform; a new write path must not reopen either (`tests/e2e/native/fs-scope.spec.ts`).
- Other apps' MCP config files make those apps start programs, so they are reached only through `mcp_client_config_read` and `mcp_client_config_write` (`desktop/src/agents/mcp_clients.rs`), never the fs scope. Each takes a client name, never a path, and a write applies only over the text the webview's edit started from and only when, read as JSON or TOML in Rust, it differs from that text by the `pairdraw` entry alone, set to that client's fixed `pairdraw-mcp` entry or removed (`mcp_clients/entry.rs`); keep those entries in step with `src/app/automation/mcp/clients/catalog.ts` (`mcp_clients` unit tests, `tests/e2e/native/mcp-clients.spec.ts`).
- A `shell:allow-spawn` entry pins the whole command line: no `"args": true`, and a Windows `.cmd` shim runs through its own `cmd-<name>` entry with fixed `/c <name> …` arguments, which `resolvePlatformCommand` selects (`tests/engine/tauri/command.test.ts`).
- A local MCP server the person configures runs only through `mcp_stdio_spawn`, or reaches a coding agent only as the program path `mcp_stdio_approve` returns, never through a shell scope: both resolve the program on the search path and go on only after a native dialog approved that program, its arguments, and its variable names, remembered in `mcp-stdio-approvals.json` in the app data folder. The shell words that dialog and its buttons itself; the webview supplies only a locale code and the connection name, which is cut to one short line. Variables that choose the program or load code are refused here and in `src/app/integrations/mcp/stdio/env.ts` (`agents::mcp_stdio` unit tests, `tests/app/integrations/mcp/store.test.ts`).
- The Software Update window is a second webview labelled `updater` that loads `updater.html` (`src/updater.ts`), never the editor's `index.html`; its own capability, `desktop/capabilities/updater.json`, grants only checking, installing, restarting, closing, and opening links. It owns no documents, so before a restart or a Windows install it asks the editor window over `updater:restart-request` to run the Quit approval (`src/app/shell/updater/approvals.ts`, `tests/app/shell/updater/session.test.ts`).
- The checked-in `tauri.conf.json` names no update feed (empty updater `endpoints` and `pubkey`, `createUpdaterArtifacts` off); only the release config adds one, so local and fork builds never offer Pairdraw releases, and a check reports updates as not set up (`tools/release/release-packages/tests/native/updater.test.ts`, `tests/app/shell/updater/check.test.ts`).
- A `.deb` or `.rpm` binary run outside the system folders, such as the portable Linux `.tar.gz`, never checks for updates, since the updater would install the system package instead; the check keys off its resource folder resolving outside `/usr/lib/` (`src/app/shell/updater/feed.ts`, `tests/app/shell/updater/check.test.ts`).
- Never click Install in a `tauri dev` build: the updater unpacks the release next to the running binary, which there is `desktop/target/debug`.
- `desktop/generated/menu.json` is produced by `bun run generate:tauri-menu` from `src/app/shell/menu/schema.ts`; do not edit or import it directly.
- A menu entry with a `feature` in the schema is built only while the frontend names that feature through `set_native_menu_features` (`src/app/shell/menu/features.ts`); every rebuild keeps the check states the menu had (`desktop/src/menu/mod.rs`).
- macOS keeps About, Check for Updates…, and Settings… in its application menu, so the builder leaves the schema's copies out there and drops a menu they leave empty, Help; on Windows and Linux, Help's About is the system About dialog (`menu::tests`, `tests/e2e/native/help-menu.spec.ts`).
- Run `bun run generate:icons --target desktop` before direct Cargo checks; native icons are generated, not committed.
- `build_fig_file` performs full `.fig` export on desktop at the level it is given, on a blocking thread, since high levels take seconds; saves that patch an opened archive compress in the web worker (`packages/fig/AGENTS.md`).
- The embedded WebDriver plugin compiles only with the `native-test` Cargo feature and must never be enabled in development or production binaries. Native tests use `bun run test:native` (`tests/AGENTS.md`).
- The editor opens external links through the `open_external_url` command, which allows only `http`, `https`, and `mailto`, and shows files linked from chat replies through `reveal_local_file`, which takes only existing absolute local paths without `..` or another computer's share; native-test builds record both for `take_native_test_opened_urls` and `take_native_test_revealed_files` instead of launching anything. The main window is built in `setup` so `window.open` goes the same way (`open_new_window_externally`); the shell plugin's own link handler is kept out by `src/app/shell/external-links.ts` (`system::opener` unit tests, `tests/e2e/native/cloud-links.spec.ts`).
- `pairdraw://` links are parsed in `desktop/src/launch/links.rs` and queued in `desktop/src/launch/mod.rs`: `open` queues files through `take_pending_open`, `join` queues validated room IDs through `take_pending_rooms` (read only by builds with `COLLABORATION_INCLUDED`), `cloud` queues Cloud invitations and shared links (UUID, hex secret, `http(s)` server) through `take_pending_cloud_links`, and `oauth/<provider>` is forwarded as an `oauth-callback` event; second launches forward their link arguments through the single-instance handler (`launch::links` unit tests).
- ChatGPT and OpenRouter sign-ins return to a loopback listener in `desktop/src/network/oauth.rs`, taken before the browser opens and closed after the one request that carries the attempt's state: ChatGPT on port 1455, the redirect OpenAI registers, OpenRouter on a port the system picks, named in its `http://localhost:<port>/oauth/openrouter` redirect (`network::oauth` unit tests, `tests/app/ai/providers/sign-in/loopback.test.ts`).
- SF Symbols are drawn by SwiftUI through the Swift package `desktop/swift/sf-symbols`, linked by `build.rs` on macOS; they are never bundled, served, or read from Apple's font files. `sf_symbols_render` stays a synchronous command so Tauri runs it on the main thread SwiftUI needs, and both commands answer null below macOS 14, which lacks the path operations that cut badge knockouts (`packages/core/tests/icons/sf-symbols/provider.test.ts`).
